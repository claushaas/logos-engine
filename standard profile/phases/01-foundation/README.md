# Foundation

Foundation defines the normative base of the project.

It answers why the project exists, what problem it addresses, who it serves, which principles guide decisions, which boundaries constrain the work, and how foundational success is recognized.

This phase must not describe implementation details, product features, market execution, or operational processes. Its job is to make the project coherent before it becomes buildable.

## Central Question

Why should this project exist, for whom, under which principles, within which limits, and with what definition of success?

## Documents

| Document | Role | Central Question |
|---|---|---|
| [Thesis](01-thesis.yml) | Defines the founding conviction behind the project. | What truth, hypothesis, or conviction justifies this project's existence? |
| [Problem](02-problem.yml) | Anchors the project in a real problem before solution design. | What pain, friction, confusion, or limitation does this project exist to address? |
| [Audience](03-audience.yml) | Clarifies who the project is for and what context they inhabit. | Who should recognize this project as useful, necessary, or inevitable? |
| [Principles](04-principles.yml) | Defines decision rules that guide future trade-offs. | What must the project favor when decisions are ambiguous or conflicting? |
| [Boundaries](05-boundaries.yml) | Protects the project from conceptual and scope expansion. | What must this project not become, do, or promise? |
| [Success Definition](06-success-definition.yml) | Defines how foundational success is recognized. | What must be true to say the project is working at a foundational level? |
| [Glossary](07-glossary.yml) | Stabilizes the meaning of essential terms. | What do key terms mean within this project, and what should they not be confused with? |

## Phase Output

By the end of Foundation, the project should have:

- a clear reason to exist;
- a specific problem to address;
- an explicit audience;
- actionable principles;
- hard boundaries;
- a definition of success;
- stable core vocabulary.

## Out of Scope

Foundation should not contain:

- product roadmap;
- feature list;
- technical architecture;
- implementation plan;
- go-to-market strategy;
- pricing model;
- operational playbooks.

Those belong to later phases.

## Completion Standard

Foundation is complete when downstream phases can use it as a decision filter.

If a later product, engineering, market, or operations decision cannot be evaluated against Foundation, this phase is still too vague.
