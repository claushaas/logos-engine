# Validation

Validation defines how the project thesis, problem, audience, assumptions, and business logic are tested before deeper product and engineering commitments are made.

It answers whether the project is desirable, plausible, testable, economically viable, and strategically worth advancing.

This phase must not define the final product specification, technical architecture, launch execution, or operational model. Its job is to convert conviction into evidence and decision quality.

## Central Question

Does the project have enough evidence, validated assumptions, and business logic to justify moving from foundation into product definition?

## Documents

| Document | Role | Central Question |

| [Validation Strategy](01-validation-strategy.yml) | Defines how validation will be approached and sequenced. | How should this project be validated before major commitments are made? |
| [Core Assumptions](02-core-assumptions.yml) | Identifies the assumptions that must be true for the project to work. | What are we assuming about the problem, audience, behavior, economics, and execution? |
| [Hypotheses](03-hypotheses.yml) | Converts assumptions into testable claims. | Which claims can be tested, falsified, or strengthened with evidence? |
| [Research Plan](04-research-plan.yml) | Defines how qualitative and quantitative learning will be collected. | How will we observe, interview, measure, or research the target reality? |
| [Experiments](05-experiments.yml) | Specifies practical tests that produce evidence. | What experiments will reveal whether the project is desirable, usable, viable, or risky? |
| [Economic Model](06-economic-model.yml) | Tests whether the basic numbers can work. | Can the project become economically sustainable under plausible assumptions? |
| [Business Model](07-business-model.yml) | Defines how the project creates, delivers, captures, and sustains value. | What mechanism makes this project economically, operationally, and strategically viable? |
| [Evidence Log](08-evidence-log.yml) | Records observed evidence without rewriting it into conclusions too early. | What evidence has been collected, and what does it actually show? |
| [Decision Record](09-decision-record.yml) | Captures validation decisions and their rationale. | What decisions were made from the evidence, and why? |
| [Validation Report](10-validation-report.yml) | Synthesizes the validation phase into a go / no-go / revise recommendation. | Should the project advance, change direction, or stop? |

## Phase Output

By the end of Validation, the project should have:

- an explicit validation strategy;
- a ranked set of core assumptions;
- testable hypotheses;
- a research plan;
- defined experiments;
- an initial economic model;
- a coherent business model;
- an evidence log;
- recorded validation decisions;
- a clear validation report.

## Out of Scope

Validation should not contain:

- final product specification;
- detailed UX or UI design;
- implementation architecture;
- database schema;
- launch campaign plan;
- sales playbook;
- operational support process;
- long-term roadmap.

Those belong to later phases.

## Completion Standard

Validation is complete when the project has enough evidence to justify one of three decisions:

1. advance to Product;
2. revise the thesis, audience, model, or assumptions;
3. stop or archive the project.

If the project advances without clear evidence, explicit assumptions, and a recorded decision rationale, Validation is still too weak.
