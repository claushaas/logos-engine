# Positioning

## Positioning Summary

LOGOS Engine should be positioned as a local-first way to clarify project intent before building. The product is strongest when described through the pain of ambiguous execution, the discipline of reviewable decisions, and the practical output of repository-native documentation.

Positioning must remain validation-safe. It can claim what the product is designed to do, but not that the market has validated the need.

## Positioning Statement

For technical and product-adjacent builders who are about to build from unclear intent, LOGOS Engine is a local-first TUI that turns project ambiguity into structured decisions, assumptions, questions, risks, and canonical documentation inside the repository.

Unlike generic chat prompts, static templates, or heavy product management tools, LOGOS Engine keeps clarification inspectable, reviewable, and connected to the project files that will guide implementation.

## Category Frame

The preferred category frame is decision-first documentation engine.

Secondary frames include structured intent documentation tool and local-first project clarification TUI. The category should be tested in discovery because it may be unfamiliar to new audiences.

## Target Customer Context

The target customer is a builder who can move quickly from idea to code, but knows that speed can amplify vague decisions. They want enough structure to guide execution without adopting a large process or moving their project reasoning into a remote workspace.

## Primary Pain

The primary pain is building from unclear intent. This appears as scattered notes, vague product decisions, repeated rework, brittle AI prompts, missing assumptions, and implementation work that starts before the project is explicit enough.

## Alternatives and Substitutes

Alternatives include generic AI chat, PRD templates, Notion pages, Markdown docs, project management tools, consultants, design workshops, and immediate coding.

LOGOS Engine should acknowledge these alternatives instead of pretending users currently have no solution.

## Differentiated Value

The differentiated value is not that LOGOS Engine writes documents. The value is that it turns clarification into structured, reviewable state and renders documents from that state.

This makes the documentation easier to inspect, regenerate, validate, and use as context for future work.

## Differentiators

Key differentiators are:

- Runs locally from the project repository.
- Uses a TUI workflow instead of a SaaS workspace.
- Treats profile YAML and structured state as source of truth.
- Renders canonical Markdown documentation into a configurable root, defaulting to `logos/`.
- Produces derived HTML artifacts and agent packs.
- Keeps deterministic validation separate from AI judgment.
- Requires explicit user review of proposed decisions.

## Reasons to Believe

Current reasons to believe are product design reasons, not market proof. They include the repository-native workflow, local-first constraints, structured decision model, Standard profile coverage, and the founder's direct experience with unclear pre-build project intent.

External proof remains missing and must be created through validation.

## Proof Hierarchy

The proof hierarchy should evolve in this order:

1. Product demo and sample output.
2. Soft-launch usability feedback.
3. Evidence that users complete a clarification cycle.
4. Evidence that generated docs help users make better next-step decisions.
5. Evidence of repeated use, contribution, referral, or willingness to pay.

## Claim Boundaries

LOGOS Engine may claim that it helps structure decisions and generate documentation from reviewed project intent.

It must not claim validated demand, startup success, market fit, better product outcomes, reduced failure rates, pricing fit, retention, or revenue potential.

## Messaging Pillars

The messaging pillars are:

- Clarify before building.
- Decisions over vibes.
- Local-first and repository-native.
- Reviewable AI assistance.
- Documentation that can guide humans and agents.

## Narrative Frame

The narrative is that modern builders can execute faster than they can clarify. LOGOS Engine helps restore the missing layer between idea and implementation: explicit decisions, visible assumptions, open questions, and documents that can be trusted because they were derived from reviewed state.

## Anti-Positioning

LOGOS Engine should not be positioned as:

- An AI startup generator.
- A business validator.
- A replacement for customer discovery.
- A generic documentation writer.
- A project management suite.
- A no-code builder.
- A hosted collaboration platform by default.

## Positioning Risks

The main risk is that users hear "AI writes docs" and miss the decision-first product model. Another risk is category confusion: the product may sit between documentation, product planning, and developer tooling without a familiar name.

Positioning should be tested through short descriptions, landing page copy, demos, and direct feedback.

## Downstream Handoff

This positioning informs messaging, landing page copy, launch posts, demos, community descriptions, and sales/discovery scripts.
