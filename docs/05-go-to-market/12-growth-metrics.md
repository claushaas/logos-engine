# Growth Metrics

## Growth Objective

Growth metrics should measure whether LOGOS Engine creates qualified learning and meaningful activation. The goal is not to inflate attention, but to understand whether the product helps builders clarify real projects.

## Growth Model

The initial growth model is open-source discovery plus local activation:

Qualified builder sees product -> understands use case -> tries in a repository -> completes clarification -> generates useful docs -> provides feedback or returns.

## North Star Metric

The early North Star Metric is qualified activated users who complete a clarification cycle and report that the output made their project clearer.

This metric may be measured manually during early validation.

## Input Metrics

Input metrics:

- Qualified outreach sent.
- Demo assets published.
- Community posts published.
- Discovery conversations completed.
- README and onboarding improvements shipped.
- Sample projects created.

## Acquisition Metrics

Acquisition metrics:

- GitHub repository visits.
- Stars and watches.
- Clones or install attempts, where available.
- Demo views.
- Landing page visits.
- Community post engagement.
- Direct outreach replies.

## Activation Metrics

Activation metrics:

- First successful TUI run.
- Provider configured.
- Workspace initialized.
- Clarification cycle completed.
- Proposed decisions reviewed.
- Markdown generated.
- User reports clearer next step.

## Conversion Metrics

Early conversion metrics:

- Visitor to install attempt.
- Install attempt to successful run.
- Successful run to generated docs.
- Generated docs to feedback.
- Demo conversation to trial.

Payment conversion is not relevant until pricing is validated.

## Retention Metrics

Retention metrics:

- Repeat run on the same project.
- Subsequent document generation.
- Return after implementation progress.
- Use on a second project.
- Follow-up feedback after initial activation.

Retention evidence is currently missing and should be a validation priority.

## Referral Metrics

Referral metrics:

- Repository shares.
- User recommendations.
- Mentions in communities.
- Contributions or issues from users.
- Users inviting other builders to try.

## Expansion Metrics

Expansion metrics:

- Requests for custom profiles.
- Requests for team review.
- Consultant or agency use cases.
- Support or hosted workflow requests.
- Commercial usage inquiries.

Expansion should remain exploratory.

## Revenue Metrics

Revenue metrics are deferred. No revenue target should be used for MVP GTM.

Future revenue metrics may include paid pilot interest, support contracts, sponsorships, hosted conversion, or commercial license inquiries.

## Channel Metrics

Channel metrics:

- Qualified traffic by source.
- Activation by source.
- Feedback quality by source.
- Objection themes by source.
- Contribution or referral by source.

## Cohort Metrics

Cohorts should be tracked by launch wave, source channel, segment, version, and onboarding path.

Small qualitative cohorts are acceptable and preferable to noisy aggregate metrics.

## Quality Metrics

Quality metrics:

- User-rated clarity improvement.
- Number of useful decisions identified.
- Number of unresolved assumptions surfaced.
- Output usefulness for next implementation step.
- Frequency of generic or misleading generated content.
- Setup issue frequency.

## Guardrail Metrics

Guardrail metrics:

- Unsupported claim incidents.
- Privacy or trust concerns.
- Hidden telemetry concerns.
- Provider setup confusion.
- Output root confusion.
- Generated content requiring heavy correction.
- Users expecting business validation.

## Metric Definitions

Metrics should have clear definitions. For example, activation requires completed clarification and generated docs, not merely installation.

Feedback quality should be judged by specificity, connection to actual use, and whether it informs a product or GTM decision.

## Metric Thresholds

Formal thresholds are not established. Early thresholds should be used as review triggers, not rigid success claims.

Example review triggers:

- High install drop-off: review README and setup.
- Low activation after setup: review TUI flow and examples.
- Positive feedback without repeat use: investigate retention.
- High confusion about claims: revise messaging.

## Reporting Cadence

During launch, metrics and feedback should be reviewed weekly.

After the first public launch cycle, the team should run a structured evidence review before expanding channels or pricing work.

## Metric Ownership

Metric ownership sits with the product/founder role until a dedicated GTM process exists.

Engineering owns product events only if instrumentation is explicit, optional, and consistent with local-first trust.

## Metric Risks

The main metric risk is confusing attention with validation. Stars, views, and likes can help, but they do not prove that the product creates value.

Another risk is adding invasive telemetry that conflicts with the product's local-first promise.

## Downstream Handoff

These metrics inform launch review, channel decisions, product prioritization, pricing readiness, and GTM risk management.
