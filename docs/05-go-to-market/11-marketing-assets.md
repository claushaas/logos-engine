# Marketing Assets

## Asset Objective

Marketing assets should make LOGOS Engine understandable, testable, and trustworthy for qualified early builders.

The assets should show the workflow and outputs clearly while avoiding claims of validated demand, pricing fit, or business outcomes.

## Asset Taxonomy

Asset categories:

- Core product explanation.
- Installation and onboarding.
- Demo and walkthrough.
- Sample project output.
- Launch communication.
- Feedback capture.
- Support and troubleshooting.
- Proof and evidence updates.

## Asset Inventory

Initial asset inventory:

- GitHub README.
- Installation guide.
- Product landing page or project page.
- Short terminal demo.
- Sample repository.
- Example generated Markdown set.
- HTML artifact example.
- Agent pack example.
- Launch post.
- Community post templates.
- Feedback issue template.
- FAQ and limitations page.

## Asset Priority

Highest priority assets are README, installation guide, demo video, sample project, and before/after documentation examples.

These assets reduce the biggest GTM risk: users understanding the idea but not seeing how it works.

## Landing Page

The landing page should explain:

- What LOGOS Engine does.
- Who it is for.
- When to use it.
- How the local workflow works.
- What files it generates.
- What it does not validate.
- How to try it.

The page should avoid broad founder-success claims.

## Website Copy

Website copy should use practical language:

- "Clarify before you build."
- "Turn ambiguous project intent into structured documentation."
- "Run locally from your repository."
- "Review decisions before docs are generated."
- "Use generated docs, HTML artifacts, and agent packs as implementation context."

## Email Assets

Email assets may be useful for founder-led outreach and follow-up.

Initial emails should be short and specific: identify the pain, show the demo, ask whether the builder has a real project where unclear intent is currently costly.

## Social Assets

Social assets should include short clips, before/after file tree screenshots, concise positioning lines, and transparent build-in-public updates.

They should not rely on exaggerated AI claims.

## Demo Assets

Demo assets should include:

- Terminal recording from repository setup to generated docs.
- Sample project walkthrough.
- Before/after documentation tree.
- Decision review moment.
- Generated Markdown preview.
- HTML artifact preview.
- Agent pack preview.

## Product Screenshots

Screenshots should show real interface states:

- TUI start.
- Provider configuration guidance.
- Clarifying conversation.
- Proposed decisions.
- Diagnostics or status.
- Generated `logos/` structure.

Screenshots should be readable and should not hide unfinished rough edges behind abstract imagery.

## Explainer Video

The explainer video should be short and workflow-first. It should show why ambiguity matters, how LOGOS Engine runs locally, and what output appears in the repository.

The video should not imply that LOGOS Engine validates the business.

## Sales and Pitch Materials

Sales materials should support founder-led discovery rather than enterprise selling.

Useful materials include a one-page overview, demo script, objection responses, sample output, and feedback guide.

## Press Kit

A lightweight press kit may include logo, product description, screenshots, founder note, repository link, and claim-safe boilerplate.

This is optional until public launch.

## App Store / Marketplace Listing

Marketplace listings are deferred. If package registries or open-source directories require descriptions, they should reuse the approved short description and claim boundaries.

## Partner Assets

Partner assets may include a teaching guide, consultant walkthrough, sample client baseline, or open-source maintainer example.

These should wait until partner interest is observed.

## Support-Adjacent Assets

Support assets should include troubleshooting, provider setup guidance, known limitations, FAQ, and issue templates.

Support content is part of GTM because setup failure can look like market rejection.

## Tracking and Attribution Assets

Tracking assets should remain privacy-safe and explicit.

Useful assets include optional feedback forms, issue templates with source fields, community post links, and manual cohort tags.

## Asset Production Workflow

Asset production workflow:

1. Draft from approved positioning and messaging.
2. Check against validation boundaries.
3. Verify product behavior in a real repository.
4. Capture screenshots or recordings from current product state.
5. Review for clarity and unsupported claims.
6. Publish and collect feedback.

## Asset Approval Workflow

Assets should be approved against these checks:

- Does it show the real product?
- Does it explain the local workflow?
- Does it mention the default `logos/` output root correctly?
- Does it avoid validation claims?
- Does it clarify what the product does not do?
- Does it include a concrete next step?

## Asset Readiness Checklist

Asset readiness checklist:

- README complete.
- Installation verified.
- Demo recorded.
- Sample project available.
- Generated output reviewed.
- Feedback path included.
- Unsupported claims removed.
- Known limitations included.

## Asset Maintenance

Assets should be reviewed after major workflow changes, profile updates, launch feedback, and changes to output structure.

Outdated screenshots or examples can damage trust, especially for a local developer tool.

## Asset Risks

Risks include assets that feel too abstract, show outdated behavior, overpromise AI capability, hide setup complexity, or fail to show generated outputs.

## Downstream Handoff

This asset plan supports launch execution, channel experiments, sales discovery, and growth measurement.
